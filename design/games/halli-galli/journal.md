## 仲裁记录

### A1 张数与每种张数：56 = 4 × 14

S1/S3/S4 均明确 56 张；S3 逐项列出四种水果各 14 张。S5 也是 56 张、4 种。**定案 56 张、每种 14 张。**

### A2 数量分布：1×5 / 2×3 / 3×3 / 4×2 / 5×1

S4 与 S5 的指南页给出完全相同的分布；两者独立表述且数学自洽：

- 张数：5 + 3 + 3 + 2 + 1 = **14 张/种**，×4 = 56 张 ✓
- 水果面：1×5 + 2×3 + 3×3 + 4×2 + 5×1 = 5+6+9+8+5 = **33 个/种**，×4 = 132 个 ✓
- 每张牌至少 1 个、至多 5 个，与"单张 5 个也算"的规则吻合（每种恰有 1 张 5 个的牌）✓

**定案采用该分布。** 该分布是后续引擎测试与素材生成的依据（20 种牌型 × 张数）。

### A3 水果命名：李子 vs 樱桃 vs 青柠 vs 葡萄

来源存在版本差异：

- S3（中文最大流通版本）：草莓、香蕉、柠檬、**李子**
- S4：bananas, plums, lemons, strawberries → **李子**
- S5：香蕉、草莓、**樱桃**、青柠
- 百度百科英文页：同一页面内自相矛盾——概述写 cherry，规则段写 plum/grape
- 另一英文实现（hanpann）：strawberries, bananas, **grapes**, **limes**

仲裁：**采用 香蕉/草莓/柠檬/李子**。理由：原版 Halli Galli（Haim Shafir, 1992）为 plum；中文最广流通版为"李子"；S4 与 S3 两个独立来源一致；樱桃/青柠/葡萄均出现在重制版或第三方实现中，不作为基础版依据。

> 线上素材只需 4 种水果，命名差异不影响规则；若后续换主题皮肤，替换 `design/games/halli-galli/game.yaml` 的水果 key 即可。

### A4 牌堆耗尽后的抢铃权（未定案，需产品拍板）

- S1：牌堆耗尽即"drop out"，明牌留在桌上直到被赢走。
- S2：牌堆耗尽即 out，明牌 stays and counts。
- S5：牌堆抽光但明牌仍在桌上时，**仍可参与抢铃**；直到有人按对收走全桌牌，或自己按错赔光，才正式出局。

S1/S2 与 S5 冲突。线上实现建议：

- 默认按 S1/S2：**轮到自己翻牌且牌堆为空 → 标记出局**；明牌保留计数。
- 保留开关 `allowRingAfterExhausted`（默认 false），若要复刻 S5 口径可开启。
- 该选择直接影响淘汰提示与终局判定，列为准备计划 **D4** 待拍板。

### A5 两人残局的特殊裁定

S1/S2/S3/S5 一致：只剩 2 人时，若有人抢错铃，**对手直接赢走桌面全部牌，游戏立即结束**。定案采用。

### A6 水果组合改判：苹果 / 柠檬 / 樱桃 / 葡萄（2026-11-21）

A3 原本按 1992 原版口径取"香蕉/草莓/柠檬/李子"。实际开始做素材时，已备好的四张图标是**苹果、柠檬、樱桃、葡萄**（重制版组合），且这四种恰好覆盖了 A3 里认定属于"重制版/第三方实现"的那一档。

改判理由：

1. **素材先到位**：4 张图标风格统一（粗描边 + 左上方高光），已抠底成 256×256 透明 WebP，重做为香蕉/草莓/李子要额外付出 3 张生成成本。
2. **规则零影响**：牌堆只依赖"4 种 × 各 14 张"，水果身份是纯展示层。改枚举 code 不影响任何判定逻辑、分布与终局条件。
3. **可辨识度更好**：苹果/樱桃为红色系但剪影差异大（圆果带梗 vs 双果长柄）；柠檬/葡萄颜色与形状都不冲突。原方案里香蕉与柠檬同为黄色系，小尺寸下有混淆风险。

影响面（已全部同步）：后端 `Fruit` 枚举、牌堆生成、前端 `FRUITS` 常量与素材路径、规则文案、设计数据集 `game.yaml`、校验用例。**A3 保留作为决策历史，不再代表当前口径。**

## 对线上实现的影响（供准备计划引用）

1. **并发抢铃是核心难点**：这不是回合制游戏，任一玩家在任意时刻都能发 RING。服务端必须串行化判定并记录到达顺序，不能复用 Splendor 的"当前行动方"校验。
2. **状态极小**：只需维护每位玩家的牌堆张数、当前顶牌、在/出局状态、桌面归属。快照可全量广播（手牌内容对所有人都是隐藏的，无需个性化裁剪）。
3. **延迟即公平性**：以服务端收到 RING 的顺序为准；客户端只做本地节流防误触，**不锁死按钮**（口径见 A7）。
4. **翻牌方挂机会卡住全场**：需要回合超时/托管机制，公共层目前没有，需在游戏内实现。
5. **牌型数据量小**：20 种牌型、56 张，可放代码常量或 `halli_galli_card` 表；不需要 Splendor 那样的启动缓存与 90 行种子。

## A7 交互口径：翻牌与拍铃都必须"手在卡堆上"

线上试玩暴露三个问题，一次性定下交互口径：

1. **翻牌点了没反应**，根因不在引擎：`GAME_START` 用中立视角 `toVO(null)` 广播，前端整体覆盖
   `room` 后 `mySeatNo` 变 null，`canFlip` 恒为 false。修法两层——服务端按收件人下发
   `toVO(收件人)`；前端 `resolveMySeat` 再从座位表按名字兜底（`PLAYER_JOINED` / `SEAT_CHANGED`
   仍是中立广播，必须能自愈）。
2. **抢铃删除键盘路径**：空格会让"预瞄铃"零成本——指针停在铃上，另一只手按空格即可在翻牌同一帧抢铃。
   现在拍铃只认指针点击中心铃，且对局中随时可点（仅出局禁用）。
3. **翻牌入口改为卡堆本身**：卡堆即按钮（`pointerdown`），轮到自己时脉冲高亮 + 倒计时。翻牌瞬间
   鼠标必然在自己面板，想抢铃必须移动指针，"预瞄"不成立。

原"客户端按下立即禁用按钮 300ms"作废：真正裁决在服务端，前端只做 120ms 节流，"判定中"仅 350ms
视觉反馈。锁死按钮反而会让玩家觉得"明明点了却没反应"。

## A8 房间页 UI 对齐宝石商人

1. **抢铃结果浮层可关闭**：`.flash` 从 `pointer-events:none` 改为可交互，右侧加 `×`；
   2.4s 自动消失仅作兜底，玩家可随时手动关掉，避免遮住上方玩家面板。
2. **环形面板防溢出**：面板定位改为 `--rx/--ry` CSS 变量 + `clamp(半宽/半高, 环形位置, 100%-半宽/半高)`，
   窄屏（≤720px）覆盖 `--player-half-w:66px`；牌桌 `min-height` 540→620px。任何人数/窗口尺寸下
   面板都完整留在牌桌内。
3. **等待页与顶栏同构 Splendor**：`room-bar` 加 `max-width:1400px` 与 ≤900px 单列断点；
   等待页换成 `seat-grid` + `seat-card`（号位/玩家名/在线离线/待机标记）+ `waiting-ops`
   （起身/开局/观战提示），开局按钮从顶栏移入操作区，和宝石商人保持一致。
4. **待抽取的共享代码**：两款游戏的顶栏、等待座位卡、弹层遮罩、通知条几乎逐行重复，
   建议后续抽 `RoomBar.vue` + `WaitingSeats.vue`，或最低成本把样式提为 `src/styles/_room.scss`
   mixin；本期只做 halli 侧对齐，未动 Splendor。

## A9 翻牌卡防溢出 / 播报用人名 / 公共样式提取

1. **卡堆内容改列布局**：`.p-card` 从横向 flex-wrap 改成 `flex-direction:column`，
   水果图片收进 `.p-fruits`（`max-width:100%` + 换行），`p-caption` 与 `stack-hint` 改为流内元素，
   取消绝对定位。原先 5 张图 + 角标会挤破卡堆边界。
2. **播报一律用人名**：新增 `nameOfSeat(seatNo)`（快照玩家 → 房间座位表 → `座位 N` 兜底），
   `RING_RESULT` 抢对/抢错/赔付、`FLIP_DONE` 行、`PLAYER_OUT`、等待轮次提示全部改名字。
3. **提示 3s 内淡出**：保持 2500ms + 0.5s transition 淡出，总计 3s；手动 `×` 仍可提前关闭。
4. **公共样式真正落地**：新建 `src/styles/_room.scss`，导出 `room-bar`/`round-info`/`room-waiting`/
   `afk-tag` 四个 mixin；Splendor 与 HalliGalli 两个页面都改成 `@use` + `@include`，
   删除各自重复的 ~180 行样式。`<button>` 专属的默认外观重置留在 halli 本地，不改 Splendor 观感。
