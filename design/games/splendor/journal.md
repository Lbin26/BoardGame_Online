# 璀璨宝石 设计决策与数据核对记录

## 2026-11-20 · P1 官方卡表录入（数据集定稿）

### 任务来源

`splendor-prep` 计划 P1：逐张录入官方卡表（一级 40 / 二级 30 / 三级 20 + 贵族 10），替换 `samples/splendor.yaml` 的抽象近似值。**禁止**从 samples 复制费用（samples 五色合并、费用为约值，confidence: medium）。

### 数据源与取证方法

网络搜索服务当日不可用，改经 GitHub API 定位 5 个开源 Splendor 实现，转录原始数据后写脚本程序化三方比对（人工逐张比对不可靠）：

| 源 | 形式 | 说明 |
|---|---|---|
| daniman/splendor-server `start-state-cards.json` | 90 卡 JSON | 附带卡牌 id 自编码费用校验和，转录可机器验证；银行供给（2p:4/色, 3p:5, 4p:7 + 金5）与官方一致 |
| dsmiller95/SplendorSimulator `cards.csv` | 100 行 CSV | 行内逗号经两次抓取渲染不一致，仅在与他源吻合时采信 |

比对脚本结论（转录件存于会话工作区 `splendor-src/`）：

- **一级 40 张**：三源完全一致（40/40）。
- **三级 20 张**：三源完全一致（20/20）。
- **二级 30 张**：27 张三源一致，2 张分歧（见下）。
- **贵族**：源间分歧（见下）。

### 分歧仲裁（共 4 处）

1. **二级黑卡 2VP 单色卡**：daniman 记为 `5黑`，BreckEmert/grandeur 记为 `5白`。
   裁决：**5 白**。结构论证——二级「5 同色 → 2VP」五张卡的费用构成五色的完美排列（白←红、蓝←蓝、绿←绿、红←黑、黑←白，每色恰好出现一次）；采 daniman 版则黑色出现两次、白色缺席，破坏对称。
2. **二级绿卡 1VP 混合卡**：daniman 记为 `3白2绿2红`，BreckEmert/grandeur 记为 `3白2绿3红`。
   裁决：**3白2绿3红**。结构论证——每色二级 1VP 卡恰为一张 7 费 + 一张 8 费；daniman 版绿色出现两张 7 费，缺 8 费。
3. **贵族 #4（红黑 4+4）**：grandeur `noble.h` 记为 `4绿4黑`，BreckEmert/k1nz 记为 `4红4黑`。
   裁决：**4红4黑**。结构论证——官方 10 贵族 = 五边形容 5 个相邻色对（白蓝/蓝绿/绿红/红黑/黑白）4+4 + 恰好互为补集的 5 个三色组 3+3/3/3；「绿黑对」的补集三色组在所有源中都不存在，双射仅红黑版本成立。
4. 次要源勘误记录（不采信项）：grandeur 二级红卡 `5黑` 误标 3VP（三源证为 2VP）；dsmiller CSV 个别行列错位；daniman 两张二级卡为转录笔误（上列 1/2）。

### 官方结构不变量（校验脚本的断言依据）

- 每级每色加成卡数：一级 8、二级 6、三级 4。
- 每色每级恰好 1 张 1VP（一级）/「5同色2VP + 6同色3VP」+ 两张1VP + 两张2VP（二级）/「7同色4VP、3+7=5VP、3+6+3=4VP、3+3+3+5=3VP」（三级）。
- VP 合计：一级 5、二级 55、三级 80，卡牌合计 **140**；贵族 10×3 = 30。（计划文档原写「100VP」有误，已修正。）
- 贵族：5 个相邻色对 4+4 + 5 个补集三色组 3/3/3。
- 费用上限：单色费用 ≤ 7。

### 未收录项

- 官方贵族 tiles 的人物名字（King/Queen/Duke 等）：五个数据源均未提供可靠的名→需求映射，不臆测。贵族以需求组合标识（noble-01..10），后端 noble 表种子如需中文名可后续查规则书补充。
- 城市扩展（Cities of Splendor）、Splendor Duel：不属基础版范围。

### 结论

`game.yaml` 数值 confidence 由 samples 的 **medium** 升级为 **high**（4~5 源比对 + 结构不变量双验证），可作为对局数据源与 DB 种子的单一事实来源。P2 落盘 `script/sql/boardgame_online.sql` 时直接消费本文件。
